四个支柱：AI 产出如何被掌控 the core question
整个搭建过程反复在回答同一个问题——如何保证 AI 的产出确定可验证、不破坏宿主、被强约束、有质量。
支柱 01
确定性 & 可验证性
Session = 只追加的事件日志，是单一事实源；模型历史由日志派生。验证不是事后补的测试，而是架构结构。
  • 事件溯源：日志即状态，回放/恢复 = 播种日志
  • "模型可见 ⟺ 已记录"运行时不变量
  • 日志不可变 + 深冻结（剥离引用再入日志）
  • dev 关系不变量：请求 == 日志前缀重建
  • 属性测试：生成参数 ↔ 校验器漂移检测
  • keyless 快照回放：ACP JSON-RPC + 日志 diff
  • 日志版本机制：未知事件拒绝恢复，绝不静默读坏
支柱 02
不破坏宿主系统
副作用被多层机制关进笼子：进程级沙箱 + 能力接缝 + 先读后写 + fail-closed 审批。
  • 进程沙箱：bwrap/Landlock/Seatbelt/ACL，fail-closed
  • 能力三件套：换实现永不碰模型契约
  • fs：先读后写 + 版本 CAS + 原子写（0700 临时目录）
  • 审批 fail-closed：unavailable 即拒绝，绝不开门
  • 执行管道分层：权限门 / guard / 超时 / 结果变换
  • 生命周期所有权：teardown 顺序承载持久性
  • 协作式超时 + 大输出 spill 私有文件
支柱 03
约束力（有约束的产出）
"模型不能乱来"是硬边界：每个越界行为都变成可路由、可纠正、可回滚的事件。
  • 模型边界运行时参数校验（INVALID_ARGS 反馈闭环）
  • 结构化错误分类：稳定 code 跨 seam 路由
  • 闭合 union + assertNever + 品牌 ID
  • 注册即效应：插件卸载全撤销（HMR 安全）
  • waterfall next() 语义：不调用即短路
  • guard：循环打断 + 每调用超时预算
  • 配置失败响亮报错，绝不静默回退
支柱 04
质量
核心决策（ADR 0007）：机械质量门优于散文规范——代理遵守被强制的门，远比遵守约定可靠。
  • 每文件 100% 覆盖率（CI 门）
  • max-strict TS + lint + jscpd 克隆检测
  • knip / publint / workspace 约束 / NodeNext
  • lefthook 本地 + CI 全矩阵（node 22/24/26）
  • doc-sync：文档代码块必须能 typecheck
  • 5 级测试：unit / coverage / e2e / 快照 / 浏览器
  • 验证世界而非自报；真实入口路径
方法论配方 playbook
提炼成 8 步，可直接复用到任何"从零搭 AI Harness"的项目。
先定原则，再写代码
第 2 个 commit 就是架构文档。"一切皆插件"的微内核是宪法，之后所有决策向它对齐。
选底座，并完全拥有它
Vendor 框架源码 + manifest 守卫。框架内部行为（fiber/effect/waterfall）是正确性依赖，不能被上游 RC 偷换。
第一块积木 = 可回放的核心
agent loop + 事件溯源 session 同一天落地。可回放是后面所有"可验证"的根。
边界即权力
每个能力切 SD/Provider/Consumer 三件套。沙箱/审批/scope 都是部署策略，永不混进核心。
模型边界单独设防
schema DSL + 运行时校验 + 结构化错误，把"编译期类型承诺"变成"运行时事实"。
把每条承诺变成退出码
质量门、doc-sync、vendor 守卫…… 机械检查，不靠自觉。"承诺"必须可执行。
决策记录制度化
RFC → ADR → Agent Notes 全流程。每个决定记下：为什么、放弃了什么、后果。
用代理开发，用代理审查
项目主要由编码代理开发；审查发现全部落成提交（历史里几百个 review-fix）。门是机械的，审查是语义的。
Q1 · 上下文如何规范化编写 AGENTS.md 方法论
核心不是"把 AGENTS.md 写好"，而是建立了一套 层级 + 机械门 + 生命周期 的制度，让上下文"自动保持新鲜"，并靠 CI 而不是靠人记性来保证。
问题：需求来得快去得快、代码新文档旧、多版本混杂，怎么解决？
答案是 四层机制同时生效，每一层对应一个症状：
1.1「一个事实只有一个家」的分层体系
根 AGENTS.md 只放站立命令（每条 1-3 行，链接到归属地）；架构细节去 architecture.md；类型定义去 subsystems；"为什么"去 Agent Notes；事故去 postmortem；步骤指南去 cookbook。每层只做一件事，别处只能链接，从结构上消灭"同一事实被多份文档重复然后各自腐烂"。
1.2「写当前状态，不写变更历史」
文档规范明文禁止 "previously / now / no longer / renamed / was moved"：文档永远只描述当前真实存在的机制；变更故事放 git、PR、Agent Notes、postmortem。文档里根本不允许出现历史叙述——多版本混杂从根上被禁掉。
1.3「机械门 > 散文规范」
代理遵守被强制的门，远比遵守散文约定可靠。doc-sync 门组：文档里的 ts 代码块必须能 typecheck；粘贴的类型必须与源码逐字一致；markdown 链接/锚点必须有效；事件分类必须与代码同步。文档与代码不同步 = CI 编译错误。
1.4「字数预算制」
对易膨胀文档设硬性字数上限（根 AGENTS.md ≤ 1600 词、architecture.md ≤ 1800）。加内容必须位移或压缩，否则 CI 红；超限文档冻结不能增长。加内容的那一刻就是做取舍决策的时刻。
1.5「Agent Notes 生命周期」
非平凡改动必须在同一 PR 附 Agent Note：proposed → implemented（现在时描述已装现实，代码改名/移动时 note 必须同变更更新）→ archived（冻结，manifest + hash 校验）。已装 note 里的 "should / Plan" 会被门拒绝——不许写未来时态冒充现状。
1.6「重命名账本」
发布前姿态是"地基优先于兼容性"：改名/重组自由，但必须一个词汇表、拒绝旧名、无别名。每个改名家族一张账本表（旧名 → 新名 → 理由），目录、npm 名、import、ctx 键、事件、文档全部同步。
补充：上下文到底怎么"喂"给 AI 的？——也是可验证的
上下文加载本身做成了可审计的机制（dsh-agent-instructions 插件）：
从 $DSH_HOME/AGENTS.md 开始，沿项目根到 cwd 逐目录发现 AGENTS.md/CLAUDE.md；字节相同的重复文件去重；文件被 AI 自己改/增/删后，注入 "Updated instructions" / "Instructions removed" 会话事件。基线指令以 system-reminder 形式进入持久化会话历史——上下文本身符合"模型可见 ⟺ 已记录"不变量，可回放、可审计。上下文不是靠人工每次都告知，而是持续发现、自动注入、变更通知、可回放的机制。
Q2 · 与代码无关、可迁移的工程质量经验 playbook
每条都是"方法/制度"，不含具体代码实现，可直接迁移到任何 AI 协作项目。
A机械门优于散文规范
把所有可机检的承诺变成退出码（CI 非零即失败）。"agents follow enforced gates far more reliably than prose conventions"。
B每文件 100% 覆盖率作为门，而非目标
未覆盖的行往往不是"缺测试"，而是死代码该删。门的存在强制"加代码"必须附带"删代码/测代码"的决策。
C属性测试补覆盖率的盲区
覆盖率证明"行跑过"，不证明"行为对"。fast-check 生成随机输入 + 故意破坏，首次运行就抓到真实 bug；钉住"类型承诺 vs 运行时现实"的漂移。
D决策记录制度化，且强制"备选方案"
固定骨架 Problem → Decision → Alternatives considered → Consequences。没记录"放弃了什么"的决策会反复被重开。
E快照回放：keyless 也能验证外部行为
不用 API key 就能在 CI 验证"模型/协议/用户看到的东西"：重放录制会话、diff 归一化 JSON-RPC + 重持久化的日志。
F验证世界，而非自报
e2e 断言重跑命令 / 重读文件，"a keyword probe on the agent's own output lets a cheating agent pass"。AI 说"我改好了"不算数，磁盘上的文件才算。
G真实入口路径：测发布物，不测玩具
产品可见的插件必须用真实组合（Loader + cordis.yml + 真实 bin）测试；bin 跑构建后的 lib/ 而不是源码。
H能力三件套：换实现不碰契约
每个可替换能力拆成 Service Definition / Service Provider / Consumer。消费者永远不 import 具体实现，模型看到的 schema 一字不变。
I事件溯源 + "模型可见 ⟺ 已记录"
会话 = 只追加事件日志，历史由日志派生，回放 = 播种日志。任何进入模型请求的东西必须能从日志重建，且有运行时不变量断言。
J日志格式版本化：未知即拒绝，绝不静默
单调整数版本 + 每事件 ignorable 标记。读到未知事件类型拒绝恢复而不是静默跳过——"静默跳过 = 安全失败"。
K防御模式文档化 + 审查对照
把被咬过的 bug 类别（子进程、回调、异步状态、销毁/清理）写进文档，审查时逐类对照——把"血的教训"变成可查清单。
L事故闭环：postmortem → 修复 → 门
出事故不追责，写 postmortem（记录证据），随后立刻有修复决策记录，并补上"若回归必失败"的测试。
Q3 · 工程师如何在"AI 飞快、人无法逐行 review"时掌控项目 control
皇帝不可能看每个基层的每一步——策略是：不逐行管，管"契约、证据、记录、门"。
抓手 1 · 决策记录 = AI 的"奏折"，且强制与代码同步
非平凡改动必须在同一 PR 附 Agent Note，且 implemented 类用现在时描述"已装现实"——AI 改完代码必须同时改 note 里的事实，否则门拒绝。工程师 review 时看的是 "这 PR 声称做了什么 + note 记录为什么"，而不是 2000 行 diff 的每一行。
feature → mechanism 映射表把"每个产品功能挂到哪个扩展点"写成可检查的表——架构声称"不修改 loop 就能加功能"，这张表就是证明义务。
抓手 2 · 会话日志 = 皇帝随时可查的"基层实况"
"模型可见 ⟺ 已记录"运行时不变量：AI 看到的每个 prompt、说出的每句话、调用的每个工具、每个结果，都在只追加的 session 日志里，且可由日志重建模型请求（dev 不变量断言"loop 构造的请求 == 日志前缀重建的请求"）。工程师打开任何 session 的日志/轨迹，就能看到 AI 实际干了什么——不是它汇报的，是记录下来的。
抓手 3 · 审查提升到"契约 + 变化范围"层
不逐行 review，但每个 PR 必须：① 用 change-scope 工具算出实际影响面；② 跑覆盖该 diff 的最小测试集；③ 语义审查按 skill 要点：生命周期、并发、安全、销毁、模型视角、绕过路径——"一个实质性 blocker 的短审查，好过一堆 nit 的长清单"。blocking requirements 明确列出：证据必须存在（作者跑了哪些检查、CI 覆盖什么）。"AI 说测过了"不算，要看到执行证据。
抓手 4 · 门禁让"基层吹水"失效
质量门（覆盖率、lint、类型、doc-sync、供应商清单、重复代码）是机械的、无情的：AI 写得多快，门就查得多快。验证世界而非自报保证"改好了"必须有外部事实（重跑命令、重读文件）背书；快照测试保证任何模型可见变化都会以 diff 形式出现在 PR 里。皇帝不需要每天微服私访——基层的每一步都有记录，每个汇报都有外部证据，每个承诺都有退出码。
一句话总结
工程师放弃"逐行审查"的幻觉，换取四样东西：决策记录（AI 声称的，机械强制与代码同步）、会话日志（AI 实际做的，可重建可回放）、外部证据（AI 汇报的，用世界验证）、机械门（AI 的承诺，用退出码兑现）。方向不靠盯人，靠盯记录与门。
