# 门禁分析

为会复发的发现类推荐可执行的检查。目标不是"门越多越好"，而是**让每个会复发的发现类，在 CI 里用最便宜的检查失败**。

## 类别 ↔ 门禁对照表

| 发现类 | 门禁推荐 |
|---|---|
| 死引用 / 坏链接 | CI 里做链接 + 符号存在性检查 |
| 文档膨胀（"文档又旧了"） | 对易膨胀文件做字数预算 |
| 不编译的代码块 | typecheck 或执行文档里的代码块 |
| 重复事实 | 全库克隆/重复检测 |
| 死代码 / 未测代码 | 每文件覆盖率门，不是总百分比 |
| 命名漂移 / 旧名 | 拒绝旧名检查（一个词汇表、一张改名账本） |
| 决策记录脱离现实 | 格式门：状态与位置一致、备选方案必填、已装记录禁未来时 |
| 站立指令腐化 | 新鲜度检查：指令里的命令在代码库仍存在 |

## 权衡规则

1. **三到五个高价值门，胜过二十个聪明的门。** 每个门都是要维护的代码；从不触发的门是税，不是守卫。
2. **在 CI 里失败，不只靠钩子。** 钩子检查是建议（可以被跳过）；CI 门是承诺。钩子管便宜的本地缺陷，CI 管穷尽集合。
3. **按命中率排序，不按精巧度。** 抓到最近三次回归的粗短语 grep，胜过从没触发过的优雅解析器。
4. **门只有在"回归真的让它失败"时才是守卫。** 验证每个门：制造回归、看它变红、再还原。没人见过它失败的门 = 没验证过。
5. **预算棘轮收紧，不增长。** 在预算内的文档保留余量并逐步收紧上限；超限文档冻结直到回到目标线。提高上限要理由，不是习惯。
6. **每个门都要有属主。** 没有单一个人或团队拥有门的配置，门就会和它守卫的文档一起烂掉。

## 什么时候不该上门禁

- 发现类是一次性的（单次改名、一篇烂文档）——修复它，不要门禁它。
- 检查会误伤正当内容（长的类型目录不是文档水分）——只给易膨胀文件做预算，不是每篇文档。
- 项目跑不了 CI（没有 CI、没有构建步骤）——改推钩子或 pre-push 检查，并说明为什么 CI 不可用。

## 门禁骨架范例

校准过的范例，按项目实际名字和命令调整，不是照抄。

- **字数预算**（CI 里跑）：逐个统计预算文件字数，超上限或预算文件消失（改名不得静默弄丢预算）即失败。
- **链接检查**：遍历 markdown 链接和锚点，任何目标不存在即失败；片段（#锚点）也要查，不只查整文件。
- **文档代码块 typecheck**：从属主文档抽取 fenced 块，用项目自己的 typecheck 编译；粘贴漂移即失败。
- **拒绝旧名**：维护一个词汇表；CI grep 全库，命中被拒名即失败。
- **决策记录格式**：状态行必须与记录所在位置一致；备选方案必填；已装记录拒绝未来时标题。
