# 范例与坑

给歧义发现项做判断校准的好/坏范例。范例教你判断，不是让你把文本抄进被审项目。

## 历史叙述——改写，不追加

坏（叙述变更）：

> 会话日志以前存在内存里。后来我们加了持久化。`create` API 不再阻塞。

好（陈述当前状态；故事在决策记录里）：

> 会话日志是只追加的，且已持久化。`create` 返回异步工厂。

分辨方法：好版本一年后仍然成立；坏版本只在两次提交之间成立。

## 死引用——修或删说法

坏（主题没了，说法还在）：

> 编辑用 `ctx.patch` 服务应用差异。（代码里没有 `ctx.patch`。）

好（主题以新名存活）：

> 编辑走 `ctx.fs.editText`。

好（主题已消失）：

> （删掉这句话；它描述的能力已不存在。）

## 版本混杂——选一版

坏：

> 写操作接受 `{ content }`（v1）或 `{ path, data }`（v2）。v2 格式里……而 v1 格式里……

好：

> 写操作接受 `{ path, data }`。v1 形态随上个版本移除。

两版真共存时，需要真正的版本机制——没有版本机制还混着写的文档，无论如何都是发现项。

## 矛盾的决策记录

坏（记录写旧的，代码已做新的）：

> 决策：注册表是 `Service`。（改名账本后代码叫它 `Runtime`。）

好（决策仍立、实现变了）：

> 更新记录事实：注册表是 `Runtime`。决策本身（为什么是运行时而不是存储）不变。

好（决策本身被推翻）：

> 新记录取代本记录并交叉链接。本记录按废弃规则归档或删除，绝不静默。

## 过度修正陷阱

修复时最该避免的错——犯任何一个，修复本身就是新发现项：

- **把义务翻成许可。** "不读不许写"改写成"读了就能写"是语义变更，不是清理。极性要保住。
- **把假设吹成已装。** 计划中的方案改写成当前行为（"工具强制 X"而 X 只是规划过）。当前状态散文只描述现实。
- **修剪叙述时误删真事实。** 事实和故事混在一起的段落：保留事实，只删故事。
- **丢掉 provenance。** "实测：512 层 ≈ 0.15s"——"实测"两个字是承重的；删掉就把事实变成了猜测。
- **把模型可见字符串当"文档"改。** 工具描述、prompt、诊断都是行为。改措辞需要快照背书，不能静默重写。
- **静默删除任何带决策价值的东西。** 拿不准时，先把理由存进取代记录。

## 证据标准

弱发现（观点）：

> "文档好像过时了。"

强发现（证据）：

> `docs/tools.md:34` 引用 `ctx.patch`，该名在代码中除该文件外零命中；工具现在经 `ctx.fs.editText` 分发。

强版本点名路径、行号、符号和代码侧事实。全是弱发现的报告本身就是一个发现项——说明审计没走到证据那一步。
