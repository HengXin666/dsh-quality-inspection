# 废弃决策

对每条发现定案：修复/重写/合并/归档/取代/删除。**删或归档任何东西之前先读这个。**

## 决策阶梯

逐级往下走，匹配到就停：

1. **就地修复** —— 主题还在，只是文本错了。（规则见 [stale-context.md](stale-context.md#修复规则)。）
2. **重写为当前状态** —— 主题还在，但文档描述的是旧实现。改写事实，不追加历史。
3. **合并进属主** —— 同一事实出现在多处。留一个家，其余换成链接。合并前保留全部独有理由。
4. **用新决策记录取代** —— 旧决策被推翻或替换。新记录写当前决策；旧记录按"其理由是否仍能防止诱人的错误"决定归档或删除。
5. **归档** —— 决策已完整落地、其理由不太可能指导未来工作，但仍在记录真实事物。连同理由一起冻结并标记为非权威；封存后永不修改。
6. **删除** —— 仅当理由确证不承重：无生产消费方、无当前文档呈现为可用、无测试在行使、决策价值已在他处保留（如有）。

## 规则

1. **绝不静默删除。** 删决策不记原因 = 招它复活；删文档不记原因 = 藏起它承载的知识。删除带决策价值的东西，必须同一变更里附书面记录。
2. **保留理由优先于保留文件。** 拿不准时，把理由移入取代记录，再删或归档文件。
3. **跟随项目的生命周期。** 项目若有 proposed/implemented/archived 约定，就按它废弃；绝不在旁边另造一套。
4. **先提案再执行。** 碰共享面（站立指令、架构文档、公开 API 文档）的先给提案/PR/note；不要一边"修文档"一边静默改行为。
5. **索引要诚实。** 项目若有文档索引，废弃条目要标记；索引里还像当前文档的，不算废弃。
6. **部分取代不是删除。** 只废掉一部分时，保留存活事实并交叉链接取代记录；不要为删一段过期的把整篇删掉。
7. **被否决的备选方案最后走。** 只要其理由还能防止诱人的、有意义的错误，被否决的记录就还有价值；没有诱惑了才删。

## 执行删除或归档

1. 把全部独有理由、备选方案、后果、点名覆盖缺口移入属主记录。
2. 修复每条入链——还有东西指向旧产物，废弃就不完整。
3. 文件、配套（译文、sidecar）、索引条目一起删或移——半移的文档本身就是新的过期发现项。
4. 外部复查：grep 旧名和旧路径，两者都应零命中。
